# M4: скорость и упаковка

## Гейт скорости: не пройден

Цель плана, 60 ток/с эффективных на MacBook Air M1 8 ГБ, **не достигнута**, это решение принято как факт. Чистый декод Gemma 4 E2B Q4_K_M на этой машине около 20 ток/с (M0). Спекулятивный декодинг на реальных ходах агента даёт 1,1-1,8x, то есть реальная цель на правках 25-40 ток/с. 60 ток/с и выше (105 на стендовой «правке файла») достижимы только как потолок на копировании большого куска текста из контекста. В окне карточка скорости и график подписаны «цель 60 ток/с, не достигнута на M1 8 ГБ».

## Скорость: спекулятивный декодинг

По умолчанию свой `llama-server` запускается с `--spec-type ngram-simple` (`DEFAULT_SPECULATIVE` в `packages/core/src/inference/args.ts`, размеры n-грамма 12 и 48, значения по умолчанию сервера). Режим меняется в настройках («Дополнительно → Ускорение генерации») и в `~/.gemmacode/config.json`: `{"server": {"speculative": "none" | "ngram-simple" | "ngram-map-k"}}`. Для чужого сервера по адресу настройка не действует.

Флаги проверены по `llama-server --help` (build 11669): `--spec-type`, `--spec-ngram-simple-size-n/m`, `--spec-ngram-map-k-size-n/m`. Старые `--draft`, `--draft-max`, `--spec-ngram-size-*` в этой сборке удалены. `draft-mtp` не работает: в GGUF нет MTP-слоёв. Остальные `draft-*` требуют отдельную модель, её нет.

### Что показали замеры

Машина: MacBook Air M1 8 ГБ, Q4_K_M, контекст 16K, KV q8_0, температура 0. Сырые данные: `~/Projects/m4-results/` (`results.md`, `step3/`).

| Нагрузка | none | ngram-simple | Комментарий |
|---|---|---|---|
| Стенд «правка файла» (120 строк, вывод копирует ввод) | 20 ток/с | 105 ток/с | верхняя граница, текст идентичен none |
| Стенд «чат» | 21 ток/с | 23 ток/с | черновиков почти нет, выигрыша нет |
| Настоящий ход агента, edit30, шаги с `edit_file`/`write_file` | 17,0 ток/с | 23,5 ток/с | вне записи те же прогоны тоже ускорились (16,7 → 20,7), то есть часть разницы это дрейф машины; с поправкой ≈1,14x |
| Правка в файле на 120 строк (вызов `edit_file`, 227 токенов) | 20,8 ток/с | 38 ток/с | ≈1,8x |
| edit30, успех | 25 из 30 | 26 из 30 | не хуже; гейт M1 (20) пройден, невалидных вызовов 0 |
| edit30, ход целиком, медиана | 23,0 с | 17,0 с | |

Вывод: на реальных задачах edit30 (файлы по 3-10 строк, правки по 80-170 токенов) выигрыш около 1,1-1,4x, потому что n-грамму почти не за что зацепиться: принято 25% черновика. На правке в большом файле выигрыш около 2x. Заявленные для стенда 100+ ток/с реальные ходы агента не дают, цель 60 ток/с эффективно не достигнута и без второй модели (draft) на этой машине недостижима.

Режимы `ngram-map-k` и `ngram-mod` на реальных ходах не мерили: по решению владельца длинный прогон остановили, когда прирост на ходах с записью оказался малым. `ngram-mod` по умолчанию не включён: между запросами он учится на собственных выдачах и на стендовых повторах завышает скорость, а в чате при температуре 0 его текст разошёлся с `none`.

Подбор размеров n-грамма (n=4…12, m=16…48) шёл при загрузке машины (фоновый `ANECompilerService` на 90% ядра, своп 3,6 ГБ) и ничего не показал: скорость падала от прогона к прогону независимо от параметров, а доля принятых токенов при малых n снижалась (19% и 8% в чате против нуля черновиков у n=12). Оставлены значения сервера по умолчанию.

### Формат правки (опыт 3d)

Гипотеза: код в JSON-аргументах экранирован (`\n`, `\"`), поэтому n-граммы из файла не совпадают. Она не подтвердилась: шаблон Gemma 4 пишет вызов как `call:edit_file{new_string:<|"|>…<|"|>,…}` с сырыми строками, llama.cpp сам собирает из него JSON. Прямой опыт (`step3/fmt-bench.mjs`: один и тот же файл на 120 строк, вызов `edit_file` против блоков SEARCH/REPLACE в тексте ответа):

| Задача | none | ngram-simple, вызов | ngram-simple, блоки |
|---|---|---|---|
| вставка строки (≈226 токенов) | 20,8 | 38 ток/с, принято 43% | 41,6 ток/с, принято 59% |
| переименование (812 токенов блоками, 1200 вызовом) | 14,5-19,6 | 89 | 26 ток/с, принято 31% |

Блоки не быстрее вызова, а надёжность хуже: в первой задаче модель написала путь `path/to/src/orders.ts` из текста подсказки и сообщила «изменение применено» до результата. Экспериментальный флаг не реализован: условию «≥1,5x к вызову» блоки не отвечают.

## Кэш префикса

Проверено по журналам шагов (`eval/step-log.ts`, `eval/step-report.ts`) на 30 задачах edit30 в двух режимах и на трёх ходах пользователя подряд в одной сессии (`step3/multiturn.ts`):

- Префикс (system + описания инструментов + свод проекта) между шагами и между ходами пользователя байтово стабилен. Шаг N+1 берёт из кэша 94-95% промпта и пересчитывает только новый результат инструмента (в среднем 72-94 токена против 1145 на холодном первом шаге).
- Сгенерированные токены тоже переиспользуются: медиана «потерянных» токенов на шаге равна 1. В среднем теряется 58-70 токенов: это шаги, где вызов `edit_file` шаблон перерисовывает иначе, чем его сгенерировала модель (в сумме 4,4 тыс. токенов за 30 задач, около 15 с префилла, против 400 с генерации; исправлять нечего).
- Второй и третий ход пользователя в той же сессии: из 1302 токенов промпта пересчитано 29, из 1486 пересчитано 22.
- Первый шаг сессии холодный всегда (≈1,1-1,8K токенов, 4-6 с): в системный промпт входит корень и дерево проекта.
- Не измерено: сжатие контекста (`maybeCompact`, порог 72% контекста). Оно заменяет старые результаты инструментов пометкой и сдвигает кэш с первого изменённого сообщения, поэтому следующий шаг пересчитает всё после него. Редкий случай (длинные сессии), цена до нескольких десятков секунд.
- `--cache-reuse` модель не поддерживает (сервер пишет «cache_reuse is not supported by this context»), в приложение не добавлен.

В статистику проекта добавлены `prompt_n` (пересчитанные токены), `cache_n`, доля кэша, предложенные и принятые токены черновика и режим спекуляции (вкладка «Статистика», CSV и JSON экспорт).

## Упаковка

Сборки лежат в `apps/desktop/release/` (в git не входят). Команды из `apps/desktop`:

```bash
npm run dist:mac      # dmg и zip для macOS arm64 (проверено на этом Mac)
npm run dist:linux    # AppImage и deb, x64 (настроено, не собиралось)
npm run dist:win      # NSIS, x64 (настроено, не собиралось)
npm run dist:dir      # только каталог приложения для текущей платформы, без установщика
```

Каждая команда сама собирает окно и сервис, кладёт в `resources/llama/<платформа>-<архитектура>/` закреплённую сборку llama.cpp (`scripts/fetch-llama.mjs`) и вызывает `electron-builder` по `electron-builder.yml`. Результат для macOS: `GemmaCode-0.4.0-mac-arm64.dmg` и `.zip`, по 125 МБ, приложение 284 МБ после установки. Модель в установщик не входит.

### llama-server: кладём в сборку

Решение: в установщик входит **закреплённая сборка b11669** (commit `620d2225c`, 31 МБ с библиотеками на macOS), системный `llama-server` остаётся запасным вариантом. Порядок выбора (`resolveLlamaBinary`): путь из настроек (`server.binary`), затем сборка из установщика (`GEMMACODE_LLAMA_DIR`, его выставляет оболочка), затем `llama-server` из PATH. Причины:

- Флаги ускорения и кэша проверены по этой сборке; в новых релизах llama.cpp их имена меняются (старые `--draft`, `--draft-max`, `--spec-ngram-size-*` уже удалены). Системная версия плавает: у Homebrew она другая и тянет dylib из `/opt/homebrew`.
- Официальные сборки самодостаточны: на macOS `llama-server` ищет библиотеки рядом (`@loader_path`), Metal входит; OpenSSL не нужен. Архив 12 МБ.
- Скрипт скачивает архив из релиза ggml-org/llama.cpp и сверяет SHA-256 до распаковки (хеши прибиты в скрипте из API релиза); при несовпадении ничего не распаковывается. Для Linux и Windows прибиты CPU-варианты, для `--variant vulkan` тоже есть хеши. Для macOS arm64 проверено полностью (сборка, запуск, загрузка модели); Linux и Windows архивы не скачивались, их распаковка не проверена.

### Модель: докачка при первом запуске

Модуль `packages/host/src/model-download.ts`, окно «Нужна модель» (и блок в настройках):

- Gemma 4 E2B Q4_K_M (3,1 ГБ) и по желанию проектор для фото и звука `mmproj-F16` (1,0 ГБ) из `unsloth/gemma-4-E2B-it-GGUF`. Версия закреплена коммитом репозитория, размер и SHA-256 каждого файла прибиты в каталоге (сверены с листингом Hugging Face и с файлами из M0).
- Файлы идут в `~/.gemmacode/models/`: `*.part`, продолжение запросом `Range` с места обрыва, при обрыве связи или молчании сервера 30 с до 8 повторов с нарастающей паузой, остановка кнопкой сохраняет `*.part`. Сервер без поддержки Range (ответ 200) приводит к перекачке с начала, ответ 416 или не тот фрагмент тоже.
- После загрузки SHA-256 всего файла; при несовпадении `*.part` удаляется, ошибка говорит об этом. Готовый файл получает метку `*.ok`, после неё сети не требуется (офлайн). Файл с тем же именем, положенный вручную, принимается по хешу, чужой не затирается.
- До начала проверяется свободное место (размер плюс 0,5 ГБ).
- Прогресс: байты, скорость, оставшееся время, попытка после обрыва, фаза проверки; события `model.progress`, `model.done`, `model.error`, методы `model.status`, `model.download`, `model.cancel`. По завершении модель сама подключается в настройки (адрес чужого сервера снимается).
- Проверено: 8 тестов загрузчика на локальном HTTP-сервере (полная загрузка, обрыв, остановка, Range игнорируется, битый хеш, чужой файл, 404 и 503, нет места), 2 теста хоста, шаг e2e «первый запуск» в окне, и прогон на настоящих файлах M0 (4,1 ГБ) через локальный сервер с двумя принудительными обрывами: оба файла прошли по прибитым хешам. С настоящим Hugging Face загрузка не гонялась (по решению владельца).

### Как открыть приложение без подписи (macOS)

Сборка **не подписана и не нотаризована** (сертификата Apple Developer нет): стоит только ad-hoc подпись, которая держит пакет целым, но Gatekeeper отвергает такое приложение (`spctl`: rejected). После скачивания из интернета macOS пометит файл карантином. Варианты:

1. Перетащить GemmaCode в «Программы», запустить, получить отказ. Открыть «Системные настройки → Конфиденциальность и безопасность», прокрутить вниз до сообщения о GemmaCode и нажать «Всё равно открыть» (macOS 15 и новее). На macOS 14 и старше достаточно открыть приложение правой кнопкой → «Открыть» → «Открыть».
2. Или снять карантин командой (путь поправьте под место установки):

```bash
xattr -dr com.apple.quarantine /Applications/GemmaCode.app
```

Файлы, собранные локально и не скачанные из сети, карантина не имеют и открываются обычно.

Windows: сборка NSIS без подписи, SmartScreen покажет «Неизвестный издатель» (Подробнее → Выполнить в любом случае). Linux: AppImage делается исполняемым (`chmod +x`), deb ставится как обычно.

### Проверка собранного приложения

`SMOKE_PACKAGED=1 ELECTRON_BIN=release/mac-arm64/GemmaCode.app/Contents/MacOS/GemmaCode SMOKE_MODEL=…/gemma-4-E2B-it-Q4_K_M.gguf node --experimental-strip-types scripts/electron-smoke.ts` (из `apps/desktop`): 12 из 12 проверок. Собранное приложение открывает окно, ход агента идёт через IPC, работают статистика (node:sqlite в Node Electron), встроенный браузер, терминал (node-pty из распакованной части asar), а `llama-server` запускается из ресурсов приложения (`…/Contents/Resources/llama/darwin-arm64/`) с флагами по умолчанию (`--spec-type ngram-simple`) и загружает настоящую модель.

### Не сделано

Подпись и нотаризация macOS, подпись Windows, автообновление (по решению владельца вне M4); иконка приложения (стоит стандартная иконка Electron); сборка и запуск под Linux и Windows (конфиги написаны, архивы llama.cpp для них не скачивались); загрузка с настоящего Hugging Face; загрузка с зеркала `HF_ENDPOINT` проверялась только локальным сервером.
